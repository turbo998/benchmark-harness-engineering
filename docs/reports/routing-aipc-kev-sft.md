## 1. 核心结论摘要（Executive Summary）

1. **反事实 SFT（Counterfactual SFT）带来 `+31.5` 至 `+51.6` 个百分点的准确率跃升**：
   - 未微调的发布基线 `B0`（`0.8B`）不包含企业私有规则，在 Support ID（510 问）与 Support OOD（1,011 问）上仅得 **`44.7%`** 与 **`43.0%`**，在 Assistant ID（477 问）与 OOD（951 问）上为 **`67.1%`** 与 **`65.7%`**。
   - 若不训练、仅将业务规则硬塞入 Prompt（`B0-policy`，Prompt 长度从 `~950` 字符膨胀至 `~4,600` 字符），Support ID 仅升至 **`60.8%`**，同时端侧 CPU 延迟暴增 **6.5 倍**（`666 ms -> 4,353 ms`），峰值内存增至 `3,446 MiB`。
   - 经过第二轮反事实数据增强与 4 Epoch 训练的交付配方 **`R2-C`**（`4,038` 条企业反事实样本 + `1,000` 条 `decision-v7` 回放样本，单卡 H100 NVL 训练 `22m 42s`，峰值显存 `7,475 MiB`），`0.8B` 模型在 PyTorch 下达到：
     - **Support ID**：**`96.3%`**（**`+51.6 pts`** vs `B0`）
     - **Support OOD**：**`88.4%`**（**`+45.4 pts`** vs `B0`）
     - **Assistant ID**：**`100.0%`**（**`+32.9 pts`** vs `B0`）
     - **Assistant OOD**：**`97.3%`**（**`+31.5 pts`** vs `B0`）
     - **OOD 单字段边界翻转率（312 对）**：**`48.4% -> 76.9%`**（**`+28.5 pts`**，其中天数窗口翻转从 `37.4%` 升至 `78.6%`，区域翻转从 `35.7%` 升至 `69.0%`）
     - **通用公开基准（`transfer-v4`，656 问）**：**`64.8% -> 65.2%`**（**`+0.4 pts`**，零灾难性遗忘）。
2. **事后温度校准（$T = 2.83$）实现高置信度自动放行**：
   - 4 Epoch 深度微调会使原始 Logits 过度自信；在验证集上拟合单一标量温度 $T = 2.83$ 后，argmax 准确率保持不变，Support ID 的 Brier 分数从 `0.641` 降至 **`0.063`**、期望校准误差（ECE）降至 **`0.025`**，Assistant ID 的 ECE 从 `0.168` 降至 **`0.009`**（Brier `0.003`），在 $\le 5\%$ 错误率约束下实现 ID 集 **`100.0%` 自动化覆盖率**。
3. **8-bit `Q8_0` GGUF 在 2–3 GB CPU 内存预算内无损运行**：
   - 导出的 `Contoso-Kev-0.8B-FTcf-R2C-Q8_0.gguf` 文件仅 **`775 MiB`**（`774.8 MiB`，`8.52 BPW`）。
   - 在高通 **Snapdragon X Elite (`X1E80100`)** CPU 上单问模式（2,949 次请求，并发 1）实测：Support ID 准确率 **`97.06%`**（中位延迟 **`386.34 ms`**，ECE `0.034`）、Assistant ID **`99.58%`**（**`409.32 ms`**，ECE `0.007`）、Support OOD **`88.72%`**（**`635.37 ms`**）、Assistant OOD **`96.95%`**（**`448.31 ms`**），峰值工作集内存（Peak Working Set）仅 **`2,585 MiB`（`~2.52 GiB`）**。
   - 在 3 问合并请求模式下，将 `llama-server` 参数从默认 `-c 8192 -b 2048 -ub 2048` 收紧为紧凑配置 **`-c 2048 -b 512 -ub 512`**，Windows Commit 虚拟内存从 `5,014 MiB` 骤降至 **`2,119 MiB`**（峰值工作集 **`2,196 MiB`**），且 987 道题输出概率与默认配置 **100% 逐位一致**。

## 2. 架构机理：为什么指针式决策头（Pointer Decision Head）适合端侧？

与通过自回归生成 JSON 字符串的传统因果语言模型不同，`Kev` 在 `Qwen3.5` 主干之上接了一个轻量级 **256 维指针式决策头（Pointer Decision Head）**：

1. **单次 Prefill 前向打分（零自回归 Decode 循环）**：
   - 输入序列将任务上下文、问题与候选选项拼接为单条序列，并在每个候选选项末尾放置特殊选项标记（记隐藏状态为 $h_{\text{opt}_i}$），在问题末尾放置决策触发标记（记隐藏状态为 $h_{\text{decide}}$）。
   - 线性投影层 $q(\cdot), k(\cdot) \in \mathbb{R}^{d \times 256}$ 将隐藏状态映射为 256 维向量，通过缩放点积计算每个选项的原始得分：
     $$z_i = \frac{k(h_{\text{opt}_i})^\top q(h_{\text{decide}})}{16}, \qquad p_i = \text{softmax}\!\left(\frac{z}{T}\right)_i$$
   - 由于只需一次 Prefill 即可直接从最后一层隐藏状态提取所有选项概率，完全省去了逐 Token 自回归采样与 JSON 语法解析开销；更关键的是，单个请求内可以同时回答同一工单的 3 个正交决策问题，共享同一次主干编码。
2. **全投影层 LoRA + 决策头联合微调（LoRA-All + Pointer Head）**：
   - `Qwen3.5` 混合使用了标准注意力（Attention）、前馈网络（FFN）与 **Gated DeltaNet** 线性注意力层。实验证明，微调时必须将 LoRA（`rank=16, alpha=32`）挂载到**全部投影层**（`q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` 以及 DeltaNet 的输入/输出投影），并同时解冻指针决策头参数（`decision_q, decision_k`）。
   - 对 `0.8B` 模型，总可训练参数仅 **`11.3M`（占总参数 `1.4%`）**；对 `4B` 模型，总可训练参数仅 **`33.8M`（占 `0.8%`）**。
3. **反事实边界样本构造（Counterfactual Boundary Augmentation）与通用回放（Replay）**：
   - 常规企业工单数据（`FT`，2,147 条）能让 ID 集升至 `86.5%`，但模型容易通过记住表面句式模板来“猜答案”，遇到只改动单一关键条件（如报修天数从 14 天变为 16 天、订单金额跨过审批阈值、地区从北美换到亚太、是否附带故障照片）的 OOD 样本时容易失效。
   - **Round 1 `FT-cf`（3,832 条）** 与 **Round 2 `R2-C`（4,038 条，新增 116 条区域边界样本与 90 条上门服务正样本）** 为每条基础样本构造了“仅翻转一个边界字段、标签随之翻转”的反事实配对，并混入 `1,000` 条 `evals/v7/decision-v7` 通用回放数据（`--lr 2e-5`），从而在不损伤公开基准能力的前提下，教会模型识别真正的数值与枚举边界。

## 4. 端侧量化、内存占用与跨芯片架构评测（`llama.cpp b11935`）

### 4.1 为什么混合 `Q4_K_M` 需要特殊保护，而 `Q8_0` 是 AIPC 最佳甜点？

- 将 `0.8B` 模型全量粗暴量化到 4-bit 会破坏 `Qwen3.5` 中的 **DeltaNet 状态转移投影** 与 **256 维指针决策头**，导致校准概率严重失真。
- 即使采用专门定制的混合量化策略（`Custom Q4_K_M`，`5.76 BPW`，仅对 FFN 使用 4-bit，强制保留 Attention、DeltaNet、指针头与输出层为 8-bit），文件体积从 `774.8 MiB`（`Q8_0`）缩小至 `527.8 MiB`（节省 `247 MiB`），运行时工作集内存也仅从 `2,333 MiB` 降至 `2,088 MiB`（仅省 `245 MiB`），但 OOD 准确率开始出现轻微回落。
- 相比之下，**8-bit `Q8_0`（`774.8 MiB`，`8.52 BPW`）** 与 `BF16`（`1,446.6 MiB`）相比体积减半、延迟降低 **33%**（`1,007 ms -> 674 ms`），且在精度上与 PyTorch 原生模型完全持平。

- **内存与吞吐规律**：由于 `Kev` 是计算密集型的纯 Prefill 工作负载，单实例在 8 vCPU 上于 $N=1$ 时即跑满算力（吞吐恒定在 **`~0.92–0.93 req/s`**）。调高 `-np` 不会增加总吞吐，只会按比例预分配 KV/Compute 缓冲区并造成排队延迟线性增长。在 **$N \le 4$** 时，峰值工作集保持在 **`1.67–2.24 GiB`**（严格满足 `<3 GiB` 目标）。
- **超长多轮历史边界（3k–8k Tokens）**：当直接喂入未压缩的 160 个超长客服多轮对话原始记录（3,000–8,000 tokens）时，7 个样本超出 `8192` 窗口被拒，其余 153 个样本（459 问）准确率跌至 **`44.9%`**，中位延迟升至 **`26,395 ms`**，内存升至 `5,060 MiB`。

## 6. 架构师落地方案建议（SA Prescriptive Guidance）

1. **端侧 AIPC 标准部署配方（推荐）**：
   - 选用 **`Contoso-Kev-0.8B-FTcf-R2C-Q8_0.gguf`（`775 MiB`）**，通过纯 CPU 启动：
     ```bash
     llama-server -m Contoso-Kev-0.8B-FTcf-R2C-Q8_0.gguf -c 2048 -b 512 -ub 512 --cache-ram 0 -np 1
     ```
   - 内存占用稳定在 **`2.1–2.5 GiB` CPU RAM**，单问延迟 **`386–409 ms`**，3 问合并延迟 **`635–851 ms`**。
2. **输入预处理契约（`< 2,048 Tokens` 结构化状态提取）**：
   - 严禁将数千 Token 的原始聊天记录直接塞给 `0.8B` 指针决策模型；应在前端通过确定性规则或轻量级摘要器将多轮对话压缩为 `< 1,500 Tokens` 的结构化槽位摘要，再交由 `Kev` 执行校准后的策略判定。
3. **何时升级到 `4B Q8_0`？**
   - 当部署环境具备 `>= 8 GiB` 空闲内存（`4B Q8_0` 工作集 `6,122 MiB`）且对跨领域复杂 OOD 泛化要求高于 `91%`（`4B` Support OOD `91.5%` vs `0.8B` `88.7%`）时，可切换至 `4B` 档位。
